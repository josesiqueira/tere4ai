# TERE4AI v2 full-system audit, 2026-07-20

Two waves of five agents each: five read-only deep-dive agents over the source,
then five adversarial agents (classification fuzzing, MCP/facade abuse, dump
tampering on scratchpad copies, a FRIA legal decision matrix, and a live
multi-risk MCP sweep). No paid model calls, no repo modification by any agent,
tampering only on copies. The real repo was verified untouched (git clean, both
integrity gates pass, dumps still match build_chain record 4a98820a5915).

Formatting rule: no em or en dashes.

## Headline

The graph artifacts and the transport surface are strong. Every documented
graph count holds exactly, referential integrity is clean, the build chain
recomputes byte-for-byte, path-escape guards hold, the envelope contract and
closed status vocabulary never broke across ~120k fuzzed classifier calls plus
~110 hostile MCP calls, determinism is byte-identical, and the live sweep
matched all eight expected risk categories. What the audit found is concentrated
in two structural places: the classifier's unknown-fact discipline on the Annex
III side, and the fact that integrity is a pre-publish (CI) gate, not a runtime
one.

## Ranked findings

Severity: DEFECT (wrong or unsafe output / broken contract), WEAKNESS (real gap,
not yet an incorrect answer), IDEA (hardening).

### D1 DEFECT, highest safety payoff: Annex III unknown flags are silently treated as false, so genuine high-risk systems return minimal_or_none at confidence 1.0 with empty missing_facts
Root cause: `PROHIBITION_RELEVANT_FLAGS` (classify.py) holds only the 8 Article 5
flags. The 11 Annex III umbrella flags and the 5(b)/5(c) subflags have no
unknown-surfacing. So an absent Article 5 flag drops confidence to 0.5 and is
named in missing_facts, but an absent Annex III flag is treated as false and
confidence stays 1.0. A recruitment / credit-scoring / benefits system described
without the exact flag (and with a non-canonical domain token) is returned "not
regulated", confidence 1.0, empty missing_facts, and get_applicable_requirements
then returns zero requirements. Contradicts the module's own docstring.
Confirmed by the legal-rule agent, both classification fuzzers, ~120k calls.
Fix direction: add the Annex III flags to the unknown-surfacing logic, or refuse
confidence 1.0 on a minimal_or_none verdict when Annex-III-relevant flags are
absent and the domain is non-canonical. Mirror the treatment prohibition flags
already get.

### D2 DEFECT: Article 5 prohibition flags collapse the statute's qualifiers and exceptions, so lawful systems are marked prohibited at confidence 1.0
7 of the 8 prohibition points carry a dropped element in the frozen text: (a)/(b)
"significant harm", (c) the detrimental-treatment outcome test, (d) the
"support the human assessment ... based on objective and verifiable facts"
exception, (f) the "medical or safety reasons" exception, (g) the lawful-dataset
carve-out, (h) the whole "strictly necessary for (i) to (iii)" regime. Only (e)
untargeted facial scraping is a clean 1:1. A driver-drowsiness detector (point
(f), safety) and a fact-based investigator-support tool (point (d)) are both
marked prohibited, zero requirements, "can never be made permissible". The flag
schema gives the caller no field to express the exception. Confirmed by the
legal-rule agent and a fuzzer.
Fix direction: split the qualified prohibition flags so the exception is an
expressible fact (like the 5(b) carve-out pattern), and/or drop confidence and
route to human review when a prohibition flag is true but its
exception-relevant facts are unknown.

### D3 DEFECT, architectural: integrity is enforced only in CI, not at runtime load
The build-chain checksum and span census live only in pytest. The server's dump
load is a bare json.loads with no dump-level checksum, no gate-G4 re-check, and
it never dereferences judge_run_id. On scratchpad copies the tampering agent
served: a forged "accepted" verdict pointing at a non-existent JudgeRun; a norm
with a rewritten actor/object; an accepted alignment with both evidence sides
emptied. The one live protection is per-span snapshot sha256 (which correctly
caught snapshot tampering). Threat model note: in self-hosted Mode B the consumer
owns the dump, so the practical risk is accidental corruption or a bad
publish, not a malicious insider; but the "evidence-gated" claim is stronger if
the runtime re-verifies.
Fix direction: recompute the build-chain (or a dump-level checksum) against the
matching build_chain_*.json at load; optionally re-assert G4 and JudgeRun
existence at serve time.

### D4 DEFECT (F6), honesty-relevant: the F4 fix is inert on the production serving path
source_text was added to the runtime grounding judge's digest field list, but
norms_core.json does not carry that field and the MCP evidence/backlog tools
never resolve it, so at real serving time the evidence generator prompt renders
"Verbatim legal source text: (not provided)" and the judge digest source_text is
None. The paraphrase-drift check the F4 fix was meant to enable is still blind in
production; only the alignment CLI resolves source_text. The runtime_grounding
prompt also never instructs the judge to use verbatim wording.
Fix direction: resolve each cited norm's source span to text at serve time in
evidence.py / backlog.py (reuse the span resolver), and add the verbatim-wording
instruction to prompts/runtime_grounding/v1.md.

### D5 DEFECT, legal (under-inclusive): the FRIA point-2 exception erases a multi-area public-body obligation
annex_iii_category is the first match in point order. A system that is both a
point-2 (critical infrastructure) system and, say, a point-6 (law enforcement)
system deployed by a public-law body returns a confident does_not_apply, because
the point-2 branch returns before the deployer triggers are checked. Article
27(1)'s exception is scoped to the point-2 AREA, not the whole system, so the
point-6 aspect for a public body triggers the FRIA. The 5(b)/(c) overlap is
already guarded (returns unknown); the deployer-trigger overlap is not, and the
outcome flips on scan order, which is not a legal criterion. Confirmed by the
FRIA-matrix and legal-rule agents.

### D6 DEFECT: FRIA returns a settled "applies" while the parent classification is requires_human_review
assess_fria_applicability branches on risk_category only. When high_risk is
provisional because a prohibition flag is unknown (envelope status
requires_human_review, confidence 0.5), FRIA still returns "applies" with empty
missing_facts. If the unknown resolves to prohibited, FRIA should be
does_not_apply. The block asserts a settled obligation on a possibly-prohibited
system and does not name the dependency. 499 cases in the fuzz sweep.
Fix direction: pass the unsettled-prohibition signal (or the envelope status)
into the FRIA rule and degrade to unknown, naming the pending prohibition facts,
exactly as the 6(3)-candidacy block already does.

### D7 DEFECT: dual-route 6(1)+6(2) systems skip the 6(3) candidacy check
When the ladder returns at the 6(1) route, article_6_3_exception_candidate is
False, and the FRIA wrapper re-scans Annex III for the 6(2) side but never
re-assesses 6(3) candidacy. Identical 6(2)-side facts give unknown on the
single-route path but a confident applies on the dual-route path. FRIA-matrix
Finding 3.

### D8 DEFECT, low: a homoglyph or invisible character in domain collapses high_risk to minimal at confidence 1.0
"banking" plus a zero-width space, soft hyphen, or Cyrillic first letter yields
minimal_or_none, not_applicable, confidence 1.0, empty missing_facts. Same
family as D1 (near-miss domain reads as confidently out-of-scope). .strip().lower()
does not normalise Unicode.

### D9 DEFECT, low, contract only: paid evidence tools raise ValueError on empty content instead of degrading
evidence._validate_evidence raises on empty/blank/non-string content; the MCP
wrapper does not catch it, so a consumer with model keys present gets a raw
ToolError rather than a Section 8 degraded envelope. Pre-model, so no paid call
is triggered, and the HTTP facade already handles it (422). Free tools do not
share the bug.

### Weaknesses
- W1 Judge-rejected norms/alignments are stored as LLM_CANDIDATE with review_status "needs_review", never LLM_JUDGED_REJECTED; a consumer keying on provenance cannot tell rejected from not-yet-judged, and rejected items surface in the review queue as if pending. (Serving is unaffected: it filters on judge_verdict == accepted.)
- W2 The mechanical quote-check JudgeRun and its log event carry no prompt_sha256, so the "every JudgeRun has provenance / is edit-detectable" invariant is violated for the mechanical class (fails safe: it only ever rejects).
- W3 High-risk get_applicable_requirements returns all 339 accepted norms across 27 article groups, including Article 5 and Article 50 norms not specific to the system's Annex III category. Documented contract, but it dilutes the traceability value; an actor or category filter would scope it.
- W4 Absolute filesystem paths are interpolated into degraded envelopes and span-integrity errors (info disclosure; not attacker-triggerable in a healthy install).
- W5 The new FRIA block is not advertised in SKILL.md or llms.txt (discovery drift); evaluate_project_evidence_batch is also missing from SKILL.md.
- W6 fria.py has no model-free import guard test, though DEC-14's whole defense is the trust split (sibling modules classify.py and requirements.py both have one). Highest-value missing test.
- W7 The served envelope (facade/MCP) is not guarded for the presence of the fria block; only the in-process unit path covers it.
- W8 docs/trustworthiness_strategies.md contradicts itself on SELF-05 (lineage section says "pending, empty PDF" while the header and references.md say registered and held); it also does not yet list the FRIA rule as a strategy.
- W9 A human-confirmed (settled) Article 6(3) derogation is unrepresentable: the schema carries only the candidacy boolean, so the pipeline can only ever answer unknown once the condition flags are true.
- W10 The 5(b) fraud-detection carve-out is enforced only by a schema description string; a single elicitation error yields a confident wrong "applies" with nothing machine-checkable to catch it.
- W11 Stale build_chain records are indistinguishable from the current one (no latest marker); the base build_id is snapshot-derived and does not distinguish two builds over the same snapshot (the chain_id is the real anchor).
- W12 requirements.py actor substring match is unguarded against negation phrasing ("non-deployer" would match "deployer"); latent only, no current dump value triggers it.
- W13 The architecture diagram's service-layer box does not mention the FRIA rule (incomplete, not false; the judge diagram is correctly unaffected). Facade has no request-body-size cap and the rate limiter is in-process per-host (Phase-1 acknowledged).

### Ideas
- Sign or attest the classification so get_applicable_requirements can tell a real ladder verdict from a hand-forged classification dict.
- Replace delimiter fencing of untrusted evidence with structured role separation (the judge and mechanical quote-check are the real control today).
- Add self-contained independence guards to evaluate_evidence_batch and ground_check so they are correct in isolation, not only via their callers.
- Unicode-normalise (NFC) both sides of the mechanical quote check to remove spurious over-rejection.

## Judge-improvement ideas (B24, in-scope, trust-split and cost-safe)

Concrete options to make the LLM-as-judge more accurate and critical without
breaking the trust split or the cost discipline. None is a decided change;
each names where it plugs in and its cost posture. All pair with H1 (task 25).

1. Adversarial multi-vote on high-stakes verdicts only. For a judge "accepted"
   that feeds a prohibition or a high-risk requirement (the consequential
   subset, not every call), spawn N independent judge calls each prompted to
   REFUTE the acceptance; keep accepted only if fewer than a majority refute,
   else needs_human_review. Plugs into the verdict aggregation in
   judge/runtime_grounding.py and extract_norms/pipeline.py. Cost: N times on
   the gated subset, not the whole build.
2. Perspective-diverse verification. Instead of N identical refuters, give
   each verifier a distinct lens (span support, deontic correctness,
   condition/exception preservation, no-compliance-claim). Diversity catches
   failure modes redundancy misses. Same plug point and cost as (1).
3. Calibrate the scores once H1 labels exist. Today the five judge scores are
   recorded but uncalibrated (the categorical verdict gates). With the 50
   labels, fit a threshold on evidence_strength / judge_confidence and report
   FA/FR, so the confidence surfaced in the envelope is measured, not raw.
   Plugs into the score-to-envelope mapping. Free (uses existing labels).
4. Abstention-rate monitoring. Track the needs_human_review fraction per
   pipeline from the existing JSONL logs; a spike flags prompt or graph drift
   (and would have surfaced the D2 abstention shift immediately). Free.
5. Prompt-version A/B re-judge sampling. Periodically re-judge a random
   accepted sample under a second prompt version and route disagreements to
   human review; ties to the prompt_sha256 provenance already recorded. Small
   paid sample, cost-bounded.

## D1/D2 benchmark-delta analysis (2026-07-21, deterministic, no paid run)

Re-running the deterministic graph classifier over the 32 benchmark-sample
items that carry elicited features, against the frozen graph_build_judge
checkpoint: 22 unchanged, 10 shifted, and every shift is FROM a confident
"prohibited" (6 to transparency_only, 4 to high_risk). Inspection of the
shifted items shows all 10 now return status requires_human_review at
confidence 0.5, naming the missing fact, NOT a confident new answer. Cause:
D2's exculpating-fact model. Items 0, 1, 3 carry subliminal_or_manipulative
true but no causes_significant_harm fact, so the ban is not settled and the
system abstains to human review instead of a confident Article 5 prohibition;
item 76 is the victim-risk tool D2 correctly moved off prohibited. This is the
designed calibrated-reliance behavior (do not confidently ban without the
statutory harm/exception element), not a regression: the tool now abstains
where it previously guessed. The follow-up is an ELICITOR improvement (B25) to
extract causes_significant_harm and the other exculpating facts from the text,
which would let a genuinely harmful system resolve back to prohibited; the
paid ablation re-run (B20) would then report the refreshed headline accuracy
with this honest-abstention behavior. No classifier change is warranted.
